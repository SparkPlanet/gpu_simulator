# GPU 加速 SPICE 稀疏 LU：论文阅读清单与分析要求

## 1. 研究目标

围绕 2026 EDA 精英挑战赛“基于沐曦 GPU 的稀疏矩阵求解级电路仿真专用加速”赛题，系统研究 GPU 加速 SPICE 电路仿真中的稀疏 LU 分解、三角求解和批处理方法。

研究不只是追求单次矩阵分解的峰值性能，而是要服务于 NGSPICE 的完整求解流程：

```text
NGSPICE 建立 MNA 矩阵
        ↓
Symbolic analysis / ordering / fill-in prediction
        ↓
Numerical LU factorization / repeated refactorization
        ↓
Forward solve + backward solve
        ↓
Newton–Raphson 迭代
        ↓
Transient / Datasweep 多时间步、多 case 运行
```

最终需要回答以下问题：

- 哪些技术已经是文献中成熟的方法？
- 哪些方法可以直接迁移到沐曦 MXMACA GPU？
- 哪些方法需要根据沐曦硬件和软件栈重新设计？
- 在“沐曦 GPU + NGSPICE + Newton–Raphson + Datasweep”的特定组合中，还有哪些可实现、可验证的优化空间？

## 3. 第一批精读的 10 篇

第一批按以下顺序精读，对应上表序号 `2、3、5、6、7、8、9、10、11、13`：

1. DAC'12 GPU Sparse LU：建立 GPU 稀疏 LU 的基本概念和性能瓶颈。
2. NICSLU：理解电路矩阵结构复用、column dependency 和 CPU 并行 baseline。
3. TPDS'15：学习 task/data parallelism、level scheduling 和性能建模。
4. GLU：学习 hybrid right-looking 和 GPU 细粒度并行。
5. Dynamic GPU LU：学习动态 GPU 调度与动态并行。
6. GLU3.0：学习 dependency detection 和三种自适应 kernel mode。
7. SFLU：学习 synchronization-free 执行和 GPU 端依赖通信。
8. DAC'23 density-aware LU：学习 supernode、SpMM/GEMM 和密度自适应。
9. ISLU：学习 compressed format 中的索引预计算与复用。
10. Trojan Horse：学习多 case 小任务的 aggregate-and-batch。

这一批形成的主线为：

```text
DAC'12: GPU Sparse LU
    ↓
NICSLU / TPDS'15: structure reuse + dependency + scheduling + model
    ↓
GLU / Dynamic GPU LU: right-looking + dynamic GPU parallelism
    ↓
GLU3.0: dependency detection + adaptive kernel
    ↓
SFLU: remove global level synchronization
    ↓
DAC'23: density-aware sparse/dense computation
    ↓
ISLU: indexing precomputation and reuse
    ↓
Trojan Horse: aggregate-and-batch sparse direct solver
```

## 4. 每篇论文的统一分析模板

每篇论文必须回答以下 24 个问题。论文未说明的项目必须标记为“论文未报告”，不得凭经验补全。

1. 论文解决的核心性能瓶颈是什么？
2. 使用的 sparse LU / sparse computation 算法是什么？
3. 稀疏矩阵使用什么存储格式（CSR/CSC/COO/自定义格式）？
4. Symbolic factorization 如何处理？是否复用？
5. Numerical factorization 如何并行？
6. 如何表示和处理 column/task dependency？
7. GPU thread/warp/block 如何映射到 sparse task？
8. 如何解决 load imbalance？
9. 如何优化 irregular/global memory access？
10. 是否使用 shared memory、register 或 atomic？如何使用？
11. 如何处理 synchronization？
12. 是否使用 supernode、dense block 或 GEMM？
13. 是否针对不同 nnz、density 或 level width 使用不同 kernel？
14. CPU 与 GPU 分别负责什么？
15. 是否考虑 CPU–GPU 数据传输？是否支持 overlap/pipeline？
16. 是否利用 repeated factorization 或 repeated matrix structure？
17. 使用了哪些 benchmark/circuit matrices？
18. 对比了哪些 baseline（KLU、NICSLU、SuperLU、PARDISO、GLU 等）？
19. 主要 speedup 是多少？是算术平均、几何平均还是最佳值？
20. Profiler 或实验表明的真正瓶颈是什么？
21. 方法最大的局限是什么？
22. 哪些设计可以迁移到沐曦 MXMACA GPU？
23. 哪些设计最适合 NGSPICE Newton–Raphson 多次求解？
24. 哪些设计最适合 Datasweep 多 case 批处理？

### 5.2 2012–2026 技术演进图

技术演进图至少要包含以下五条主线：

- 算法：left-looking → hybrid right-looking → adaptive sparse/dense computation。
- 依赖：CPU preprocessing → level scheduling → dynamic scheduling → synchronization-free。
- 索引：dense workspace / compressed search → precomputed indexing structure → index reuse。
- 数据：repeated structure reuse → GPU-resident matrix/factors → minimized intermediate movement。
- 任务组织：single matrix → adaptive kernels → aggregate-and-batch / Datasweep batching。

### 5.3 实验数据使用规则

- speedup 必须同时注明 baseline、CPU/GPU 型号、精度和测量范围。
- 区分 symbolic time、factorization time、triangular-solve time 和 end-to-end time。
- 区分 cold factorization 与 fixed-pattern refactorization。
- 区分单矩阵最佳值、算术平均和几何平均，不能混用。
- 无法在沐曦平台复现的结论，只能作为设计参考，不直接作为赛题性能结论。

## 6. 面向赛题的优化方案要求

在完成文献分析后，提出 5–10 个可实现、可逐项 benchmark 的优化方案。方案应覆盖：

- Sparse LU 总体算法选择。
- Symbolic analysis 与 symbolic reuse。
- Numerical factorization 和 fixed-pattern refactorization。
- Forward/backward triangular solve。
- adaptive kernel 和 dependency scheduling。
- index precomputation/index reuse。
- memory coalescing 和 irregular access 优化。
- GPU-resident matrix、LU factors、RHS 和 solution。
- CPU/GPU overlap 与 pipeline。
- Datasweep 多 case batching。
- NGSPICE 中间层与求解器接口集成。

每个优化方案必须说明：

1. 优化对象和当前瓶颈。
2. 方法与数据结构。
3. CPU/CUDA/MXMACA 的责任边界。
4. 需要修改的项目模块。
5. 对应的 microbenchmark 和 end-to-end benchmark。
6. 必须收集的 profiler 指标。
7. 数值正确性与 pivot fallback 方案。
8. 预期收益、显存成本和失败条件。
9. 相关已有论文，以及本方案相比已有方法的差异。

## 7. 已有方法与我们方案的边界

最终文档必须把结论分为三类：

### A. 文献已有方法

例如：BTF、AMD/COLAMD、symbolic reuse、level scheduling、hybrid right-looking、GLU3.0 adaptive modes、SFLU synchronization-free、density-aware GEMM/SpMM、ISLU indexing structure、aggregate-and-batch。

这些不能直接宣称为我们的算法创新。

### B. 面向沐曦平台的工程迁移与重新优化

例如：

- 将 CUDA 的 thread/warp/block 映射重新调整为 MXMACA 最合适的配置。
- 根据沐曦 GPU 的显存、cache/shared memory、wave/warp 特征重做 kernel 参数选择。
- 将矩阵、LU factors 和 RHS 长期保持在沐曦 GPU 上。
- 将求解器接入 NGSPICE Newton–Raphson 与 Datasweep 完整路径。

这一类可以作为平台优化与工程贡献，但需慎重使用“算法创新”表述。

### C. 可能的新组合或赛题特定创新

需要通过实验确认，例如：

- 面向 Datasweep 的跨 case dependency-aware batching。
- 将 symbolic/index reuse 从单 case 扩展到同拓扑 case 簇。
- 同时基于 level width、update density、index cost 和当前 GPU 资源的统一 kernel selector。
- NGSPICE 建模、CPU 装配、H2D 更新、GPU refactorization 和求解的端到端双缓冲流水。
- 把 pivot-risk detection 与 GPU fast path/CPU robust fallback 联动起来。

这些方案只能在完成更广泛的相关工作检索与实验验证后，再判断是否具有创新性。

## 8. 建议的阅读与实验顺序

```text
阶段1：KLU + NICSLU
  → 建立 CPU baseline，记录 BTF、ordering、fill-in、pivot、flops

阶段2：DAC'12 + TPDS'15
  → 复现 left-looking GPU task/data parallelism 和内存带宽瓶颈

阶段3：GLU + Dynamic GPU LU + GLU3.0
  → 对比 right-looking、dynamic scheduling 和 adaptive kernel

阶段4：SFLU + ISLU
  → 优化 synchronization 与 compressed-index lookup

阶段5：DAC'23 + HotTiles + HSMU + Swift
  → 研究 sparse/dense tile 分类、SpMM/GEMM、shared memory 和 coalescing

阶段6：Trojan Horse + NGSPICE Datasweep
  → 研究多 case aggregate-and-batch 和端到端 pipeline
```
